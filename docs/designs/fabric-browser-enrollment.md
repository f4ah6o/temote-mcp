# Temote Fabric browser enrollment

Status: approved design implemented locally; code review and full verification are pending. No live Access configuration or credentials were changed.
Date: 2026-10-09

## Goal and boundaries

Let an owner connect a Temote Host to Fabric with one interactive command, using a browser login and OS-protected credentials. The command enrolls the Host, obtains explicit approval for a subset of the named roots already configured in the running local Supervisor, and starts the existing outbound HTTPS Fabric Link. The Link keeps its current connect, long-poll, response, and reconnect protocol. Browser-mode observation sync remains disabled until it has owner/grant/root namespace proof.

MCP caller authentication and Host enrollment are separate authorities. A Fabric OAuth login authenticates the human caller to `/mcp`; a distinct owner-host enrollment grant authorizes one Host Link and its approved root names. `host_id` remains a non-secret routing name. Neither `CLIENT_TOKEN` nor the current static host token map becomes an OAuth enrollment credential.

Native Windows remains outside the current runtime scope; Windows use continues through WSL2. A platform without an available OS credential store fails closed. The normal browser flow must not require 1Password, manual token copying, or a plaintext fallback. The first browser-authenticated release enables only owner-scoped live Host/session routing under approved roots. Existing cloud-only context, dashboard, Fabric data, interaction, mention, and observation-replica surfaces stay unavailable to Access-JWT callers until they can prove the same owner, active grant generation, and canonical root namespace. This is an intentional safe gate, not a claim that those surfaces have migrated.

## Current behavior and constraints

Before browser enrollment, `temote fabric connect` and `temote fabric link` led to the host-token `gateway-agent` parser. The federated Link sent `Authorization: Bearer <host token>`, `X-Temote-Host-Id`, and optionally Cloudflare Access Service Token headers. The Worker compared the bearer token against `HOST_TOKENS_JSON[host_id]`. `HOST_TOKEN` remains for the legacy session-oriented agent. `/mcp` separately accepts either a compatibility `CLIENT_TOKEN` or a Cloudflare Access JWT assertion. The assertion verifier checks issuer, audience, expiry, subject, and the configured email allowlist.

Cloudflare Managed OAuth access tokens are opaque values such as `oauth:...`. Cloudflare validates that bearer at the edge, then forwards a signed `Cf-Access-Jwt-Assertion` to the Worker. The Worker must validate that assertion and must not parse the opaque `Authorization` value as a JWT. Managed OAuth requires RFC 8707 resource indicators. The authorization server and protected-resource metadata endpoints, loopback authorization-code flow, short-lived access tokens, refresh grants, and expiry behavior are documented in [Cloudflare Managed OAuth](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/managed-oauth/).

The current `GatewayRegistry` is a global Durable Object for live leases, not an owner-grant database. The existing observation D1 binding is available to the Worker, but its `OBSERVATION_OWNER_ID` is a separate static scope and must not be treated as a browser user's identity.

## Identity and grant model

For a browser-authenticated request, the Worker verifies `Cf-Access-Jwt-Assertion` using the explicitly configured Access issuer and audience, expiry and not-before claims, a nonempty `sub`, and `ACCESS_ALLOWED_EMAILS`. The authorization owner key is derived from the verified issuer and `sub` (for example, SHA-256 of `issuer + NUL + sub`). Email is used only for the existing Access allowlist and transient confirmation display; it is not the durable owner key. The identity authority is this verified owner, not an individual MCP client: the current Access configuration does not provide a stable per-client principal, so all browser OAuth callers for one owner share that owner's Host grants and their root limits. A request authenticated only by `CLIENT_TOKEN` has no per-person owner identity and cannot create, refresh, or revoke a browser enrollment or access a browser-enrolled Host.

Because the Managed OAuth access token is opaque, the CLI does not infer an owner from the callback URL or token. Add read-only `GET /v1/enrollment-identity`, protected by Cloudflare Access and Worker assertion verification. It returns only a bounded `owner_key` derived by the Worker from verified issuer/subject plus an allowlisted display identity such as email; it never returns the assertion or OAuth token. The CLI must call this endpoint after code exchange and before showing or collecting owner/root confirmation. Before resuming a stored profile after token refresh or reauthentication, the CLI calls this endpoint and compares the verified owner key to the secure record. Cloudflare's token endpoint is validated for the pinned issuer/endpoint and token response shape; it is not expected to return a Worker owner key or Host grant generation. Worker grant-operation responses return the verified owner key and relevant grant generation, which the CLI compares to the identity response before any Link action. An identity mismatch creates no reservation and does not change the active Host grant or root scope. No remote reservation is created before identity and local root confirmation succeed.

Add an owner-host grant record in the existing D1 database, with at least: globally unique `host_id`; owner key; grant id; grant generation; status (`pending`, `active`, or `revoked`); a SHA-256 digest of a client-generated 256-bit random Host grant; the exact approved root-name set; an enrollment attempt id; and created/expiry/revocation timestamps. Store no OAuth token, refresh token, host grant plaintext, email, absolute root path, or Access assertion in D1. The random Host grant is sent only in `X-Temote-Fabric-Host-Grant`; D1 stores its digest. `host_id` is never accepted as proof of possession.

The Worker enrollment API encodes `expires_at` and `pending_expires_at` as Unix epoch milliseconds, matching D1/JavaScript `Date.now()`. Rust decodes these fields at the HTTP boundary to Unix epoch seconds before expiry comparisons or secure-record storage. OAuth access-token expiry is a separate internal Unix-seconds value derived from OAuth `expires_in`; it is never interpreted as a Worker millisecond deadline. Reject Worker deadline values that do not look like epoch milliseconds, and require a deadline on active and pending responses.

The first enrollment atomically reserves a globally unused `host_id` to one verified owner. A second owner cannot claim it. An active or pending record cannot be replaced by a fresh login, including another concurrent enrollment by the same owner. The first claim is authorized by the Access identity returned by `/v1/enrollment-identity` plus an explicit local confirmation that types the displayed `host_id`; the claim proves that this owner ran the enrollment on this machine, not a hardware-backed device identity. Server-side uniqueness makes simultaneous claims deterministic: only the first pending attempt reserves the id, and a different attempt gets a conflict without disclosing its owner. Re-enrollment after expiry or revocation is allowed only for the same owner key, with the observed grant generation and a fresh local confirmation. Retain a revoked tombstone so a stale Link or racing request cannot silently recreate a grant.

The global collision check also includes every key in `HOST_TOKENS_JSON`, whether or not that Host currently has a lease. Before allowing any browser reservation, require a present, strictly valid JSON object whose keys are valid host ids and whose values are nonempty strings; any missing, malformed, unreadable, or invalid entry disables browser enrollment and browser Link authorization. An explicitly empty legacy inventory is `{}`. Any id in that map conflicts with browser enrollment. Conversely, any pending/active/revoked browser record blocks legacy static-token authentication for the same id. The Worker checks both authorities on every Host request; absence of a current lease never releases an id.

The `GatewaySession` object keyed by `host:<host_id>` and the live registry record both carry `auth_mode`, `owner_key`, `grant_id`, and `grant_generation` for browser mode (and an explicit legacy mode for old static-token Links). Connect, poll, respond, route, and response-return checks require the exact same transport auth context. An unexpired object with a different mode, owner, or grant generation cannot be replaced by connect. Migration from static credentials is an explicit operator sequence: remove that host id from the static map, verify legacy authentication is denied, fence the old transport generation or wait for its lease to expire, then enroll the browser grant. No automatic migration is performed.

The Worker requires all of the following for the new Link mode: a valid Access assertion; an active, unexpired owner-host grant matching the assertion's issuer/subject; the same `host_id` in every identity-bearing path, header, and request body field present on that endpoint; the current grant generation; and a constant-format digest match for `X-Temote-Fabric-Host-Grant`. Missing or ambiguous identity data denies the request. The Host grant alone does not authenticate `/mcp`; an OAuth token alone does not enroll or impersonate a Host. The Worker never falls back between browser and legacy modes after an authentication failure.

## OAuth origin and network validation

The browser client must have a non-secret, explicitly configured `expected_issuer` and exact `permitted_origins` before login. The issuer is compared as a canonical issuer string to discovery metadata; it is never learned by trusting discovery alone. The origin allowlist is a set of exact HTTPS `(scheme, host, port)` tuples for the configured Fabric resource and the selected Access authorization server, protected-resource metadata, registration, and token endpoints. No wildcard host, userinfo, fragment, non-default unexpected port, URL from an OAuth response outside that set, or endpoint supplied by an Access assertion is accepted. RFC 8707 `resource` must equal the configured Fabric origin. Missing pins or any issuer/origin mismatch stops before opening the browser or sending credentials.

Every CLI HTTP request to discovery, client registration, token, refresh, or Fabric identity/enrollment endpoints uses a dedicated client with redirects disabled, ambient proxy settings disabled, a 5-second connect timeout, a 15-second total timeout, and a per-response byte limit: 64 KiB for discovery and identity metadata, 32 KiB for client registration, and 64 KiB for token or enrollment responses. The client resolves each hostname, rejects the request if any selected address is not globally routable (including loopback, private, link-local, multicast, unspecified, and reserved ranges), and pins the validated address for the connection while retaining hostname-based TLS certificate and SNI verification. It rechecks the pinned resolution on every new connection; it must not resolve once for validation and then let a second resolver choose the socket destination. It does not follow redirects, even within an allowed origin. URL parsing rejects non-HTTPS URLs and ambiguous encodings before DNS. The one exception is the exact ephemeral `http://127.0.0.1:<port>/<random-path>` OAuth callback bound to this process; it is never used for discovery or token traffic.

The Worker uses only statically configured Access issuer/JWKS origins to verify assertions; it never fetches a URL taken from a token header or request. Its issuer/JWKS fetch also disables redirects and enforces response-size and time bounds. If the configured issuer or endpoint metadata changes, the CLI stops before sending an existing refresh token and requires an operator-reviewed configuration update plus interactive login. These checks follow the repository's bounded, no-redirect, public-address fetch pattern in `src/local_oauth.rs`.

## One-command enrollment and Link lifecycle

`temote fabric connect` and `temote fabric link` are aliases for the same onboarding and reconnect lifecycle. If a static Host token is configured through `--host-token` or the existing canonical/legacy environment aliases, either command selects the existing static Link mode. Without a Host token, either command selects browser enrollment. `temote-mcp gateway-agent` remains the low-level static compatibility command. Authentication never falls back after a selected mode fails. Static mode accepts the optional Cloudflare Access Service Token pair only when both values are present; a partial pair is an error, and either service-token value without a Host token is an error. Existing environment alias precedence remains unchanged.

The browser flow is:

1. Read the versioned secure credential record and the running Supervisor's configured root names, root-registry revision, instance epoch, and session inventory through a trusted local interface. Do not hold the state-transition lock while waiting for browser login or running the Link. Do not derive Supervisor roots from the CLI's environment. For each root, calculate a local-only HMAC fingerprint over its name and canonical filesystem identity, including the filesystem object identity, using a random key stored in the OS secure record. Compare it to the fingerprint previously approved in that record. A new Supervisor instance invalidates old session proofs and requires a fresh inventory. If the root-registry revision or any selected root fingerprint changed, stop this connect attempt; revoke the saved grant with `temote fabric logout`, then rerun `temote fabric connect` to explicitly approve the new scope. Do not print absolute paths or fingerprints. If the inventory cannot classify a root or session, stop browser Link setup. Show only root names.
2. Require the explicit issuer and origin pins described above. Discover protected-resource and authorization-server metadata over the bounded HTTPS client; validate the exact issuer, endpoints, and configured Fabric resource before opening a browser. Use the RFC 8707 `resource` value for the Fabric origin, not `host_id`. Use the configured public OAuth client id; do not dynamically register a client or embed a client secret. Start a temporary listener on `127.0.0.1` at an ephemeral port and use authorization code + PKCE S256, random `state`, and a single-use callback. Bind the callback to the exact redirect URI and state, expire the transaction after 10 minutes, and close the listener after success, failure, or Ctrl-C.
3. After the callback and code exchange, call `GET /v1/enrollment-identity` and verify the Worker-derived owner key against the locally stored owner before showing or collecting any owner/root confirmation. Then show the verified owner identity and available root names. Ask the local operator to approve the displayed Host id and an explicit subset of those roots. The default selection is empty. Explain that all browser OAuth callers authenticated as this owner share this grant, limited to the selected roots. Typing the displayed Host id confirms the initial ownership claim and prevents an accidental claim. OAuth login by itself never selects or expands roots. When a valid grant already exists, reconnect reuses its owner/root scope; changing that scope requires the same explicit confirmation and fresh local fingerprints. A different Access subject cannot adopt the existing host id.
4. Under the state-transition lock, re-read the secure record and compare its version before changing it. Generate the Host grant, attempt id, and idempotency ids on the client and persist them in one versioned OS secure credential record as a pending transaction, together with selected root names, their local fingerprints, the expected current grant generation, and pending/cancel status. If this atomic secure write fails, create no remote state. Submit only the grant digest, selected root names, attempt id, expected generation, and non-secret Host metadata over the OAuth-authenticated enrollment endpoint. The Worker creates a short-lived pending reservation with a unique-host compare-and-swap. Activate it by proving possession of the Host grant. Only after the Worker confirms activation and the local record atomically commits the matching owner and generation does the CLI start the long-poll Link. If local storage fails before activation, do not activate or start Link; cancel pending state when reachable. If storage fails after activation, retain the pending record, do not start Link, and reconcile by repeating the same activation to learn the committed generation after storage recovers. A retry reads the same attempt, grant, generation, and idempotency ids from secure storage, making a lost response reconcilable without the Worker storing or reissuing a secret. After confirmed activation, clear pending/cancel fields in the same record and retain only active credentials and scope.
5. Renew short-lived OAuth access tokens using the refresh token from the OS secure store before expiry. Under the state-transition lock, first atomically persist `refresh_in_flight` with a unique refresh attempt id, then send the request. Cloudflare re-evaluates Access policy during refresh. A transport failure is retryable only when the client can prove no request bytes were sent; after any ambiguous delivery, persist `refresh_outcome_unknown` if possible, stop the Link, and never replay the old refresh token. The already-persisted in-flight marker is treated as unknown if that update fails. `invalid_grant` requires interactive browser login. On success, atomically replace the whole credential record with the returned token bundle, incremented record version, and `refresh_commit_pending`, preserving the current Host grant, generation, root fingerprints, and any enrollment/cancellation state. Read back and verify the exact version and refresh attempt id, then atomically clear the marker before using tokens; call `/v1/enrollment-identity` and compare the owner before resuming Link. A secure-store write/read-back/marker-clear failure stops the Link as `credential_commit_failed`, discards uncommitted response tokens from memory, and requires interactive reauth before retry. A process restart that finds an in-flight, commit-pending, or unknown marker also requires interactive reauth; it never guesses whether Cloudflare rotated the token. An expired Host grant requires a fresh owner-confirmed enrollment for the same owner and expected grant generation. A revoked Host grant stops the Link and reports a bounded status; it never falls back to a static token. A user-started interactive `connect` may complete the reauthentication in the same foreground run; a noninteractive run exits with `reauth_required`.

OAuth protocol fields have narrow protocol-channel exceptions: the authorization URL carries `state`, `resource`, redirect URI, and PKCE challenge; the exact loopback callback receives the one-use `code` and `state`; the token-exchange POST body carries that code and the PKCE verifier. Keep these values out of logs, terminal output, and persisted state. The verifier and state remain process memory only and expire with the callback transaction. Never place access/refresh tokens, the PKCE verifier, or Host grant in a URL. Token exchange and refresh use the exact pinned HTTPS token endpoint. No credential may appear in command arguments, environment variables, ordinary state files, stdout/stderr, ordinary logs, approval summaries, or tool output. The versioned secure credential record is the sole persistent location for OAuth and Host credentials and pending enrollment/cancellation/retry identifiers. Enrollment, refresh, reauth, logout, and revoke serialize each finite local/D1 transition with an owner-only interprocess lock, then release it before the long-poll Link runs; do not hold it while waiting for the OAuth callback. A separate process-owned OS advisory lifetime lock prevents a second Link from starting for the same profile and is released automatically when that process exits. Revoke/logout do not need that Link lock, so they can commit while Link is active and D1 immediately denies subsequent work; signal the local Link to exit or let its next authorization check stop it. Each transition re-reads the record after acquiring the lock, while server-side uniqueness and generation checks remain authoritative across machines.

If Ctrl-C happens before pending enrollment, no remote state is created. If it happens while pending, the attempt id, grant, expected generation, and cancellation id remain in the secure record; send a best-effort cancellation with that same idempotency id, or let the reservation expire and offer retry with the same transaction. An expired pending attempt can reacquire the reservation with the same attempt id and digest only if no later attempt has claimed the Host id; an explicit cancellation is terminal for that attempt. A lost cancellation response is retried with the same cancellation id and returns the same outcome. Keep pending credentials until cancellation is confirmed or the server confirms expiry; never clear the only retry data on timeout. If local secure storage fails, do not activate or start the Link; cancel the pending record when reachable. If activation succeeds but its response is lost, repeat the same idempotent activation using the stored attempt id and grant. If the machine is offline, retain credentials and retry only the safe enrollment/activation or transport step; do not silently discard or regenerate a grant.

## Root scope enforcement

Root selection must constrain actual requests, not only describe the enrollment screen. The authorized set is the intersection of the owner's D1-approved root names, the local secure record's explicitly approved names and fingerprints, and the named roots in the exact running Supervisor instance. The Worker stores only the approved names. The Link holds the matching local names/fingerprints and the current Supervisor instance and scope revisions. The Host connect request advertises only approved root names; it must not send the full configured list and rely on UI filtering. Neither side accepts a root added only by a later environment change.

For browser-enrolled Hosts:

- `session_start` with a root-relative `path` first gets a syntax check: reject empty, absolute, `..`, encoded separator, or otherwise ambiguous first-component syntax. That check is only preliminary. The Supervisor's atomic admission operation canonicalizes the target and chooses its actual root by most-specific containment; it rejects a nested-root target if the nested root is not approved, even when its path begins under an approved outer root. It then checks the root's approved local fingerprint and exact Supervisor instance/scope revision in the same critical section that creates the session. Until managed `source` provisioning can prove its allocated root is in the approved set, reject that form for this auth mode.
- Every existing-session operation, including session info/list/stop/restart and session-bound task, evidence, or job calls, must resolve the target session to its recorded canonical root identity and verify the exact session instance/epoch, approved root fingerprint, current owner/grant generation, and scope revision before forwarding. Do not authorize based only on caller-supplied `host_id`, `session_id`, path, or metadata.
- Host/session discovery is filtered to hosts owned by the caller and sessions under approved roots. An unclassifiable session is omitted and cannot be operated on. A host/session lookup that cannot establish the caller's owner grant or root membership fails closed.
- The Link repeats the same admission check before sending a routed RPC to the Supervisor. The Supervisor remains the final authority for path containment, normal-sandbox session rules, and local approval. A remote grant never adds a root to the Supervisor or changes its permissions.

This requires both a read-only Supervisor inventory and a dedicated internal atomic `admit_fabric_operation` contract. The inventory maps every remotely addressable session to canonical root identity, scope revision, and exact process/session instance. The admission contract receives a private typed context created by the authenticated Link from the D1-authorized grant and secure local record; it is not an MCP request field, public RPC parameter, or `_meta` value. In one Supervisor critical section it (a) confirms the captured Supervisor instance and root-registry revision are current, (b) resolves the actual root for a start path or exact existing session, including most-specific nested-root resolution, (c) compares that root's local fingerprint with the explicitly approved fingerprint for the same name, (d) checks the D1-authorized root-name subset and active grant generation carried by the trusted Link context, and (e) creates or admits the operation with an opaque scope proof bound to the session instance and root fingerprint. Every later operation and response routing validates that proof against the exact live session instance. Public caller metadata cannot construct or override it. If any check cannot occur atomically or any revision changes, reject the operation before dispatch.

For an existing-session call, the Worker performs a safe live inventory read and captures only the selected `{session_id, session_instance}` UUID pair in a private transport field. It strips the pair from the MCP arguments and from the public `session_list` result. The Durable Object binds that exact pair to the pending request and requires it unchanged on the Link response. The Link forwards it through a private local control request; the Supervisor compares it to the current session while holding its transition lock before any task/evidence/job or lifecycle side effect. Before returning a non-terminal result, the Link asks the Supervisor to revalidate the same pair and discards the result if the session changed. `session_stop` and `session_restart` complete their authorized transition under that lock, so they do not require the old instance to survive the response check. `session_list` and `session_start` have no existing-session binding: list returns only safe root/session fields, while start is checked against the current root registry inside the Supervisor.

The first typed live-operation allowlist is exact: `codex_status`, `codex_task_start`, `codex_task_get`, `codex_task_control`, `evidence_read`, `task_list`, `poll_job`, `job_list`, and `stop_job`, plus the separately guarded Host/session lifecycle tools. Calls retain their generated argument schemas, require explicit `host_id` and `session_id`, and mutations require a UUID `operation_id`. Other backends, raw operations, cloud data, interaction, mentions, and provisioning stay denied.

On Supervisor startup, compare all configured root fingerprints, root-registry revision, and the Supervisor instance epoch to the values in secure local enrollment records. A changed name-to-canonical-root mapping, filesystem object identity, or root-registry revision suspends the browser Link and requires the owner to explicitly reapprove the affected root names; never silently carry approval to a remapped directory. A new instance epoch invalidates existing session scope proofs but does not by itself revoke unchanged root approvals; create fresh proofs for the new instance after verifying fingerprints. Check root identity again during each atomic admission so symlink retargeting or filesystem replacement while the Supervisor is running also fails closed. Keep absolute paths and fingerprints local; never return them to the Worker, user-facing output, or logs. If the running Supervisor cannot provide this inventory and atomic contract, browser-enrolled Link setup and root-scoped routing remain unavailable. `temote fabric connect` reports the required capability and leaves the existing process untouched; it must not stop, restart, or rewrite roots. The operator can configure the root registry and perform the normal controlled Supervisor upgrade/restart separately, then retry. Root configuration is immutable for a running Supervisor. After startup, a newly configured root is not visible until that normal restart and must be explicitly approved before Fabric advertises it.

## Worker and protocol changes

Add explicit browser enrollment operations, for example read-only `GET /v1/enrollment-identity`, `POST /v1/enrollments`, `POST /v1/enrollments/{host_id}/activate`, `DELETE /v1/enrollments/{host_id}/pending`, and `DELETE /v1/enrollments/{host_id}`. Each operation requires a verified Access JWT assertion; none accepts `CLIENT_TOKEN`. Enrollment and activation use the client-persisted attempt id and expected row generation; cancellation and revocation use client-persisted operation ids. Repeating an id with identical parameters returns the original outcome; reusing it with different parameters is a conflict. Attempts are one-shot: a cancelled, expired, activated, or revoked attempt id cannot be reused for another reservation. A new attempt may replace an expired or revoked row only when its owner key matches and the client supplies the exact current row generation; an unexpired active or pending row cannot be replaced, including by a fresh login from the same owner. OAuth token refresh uses the discovered Cloudflare token endpoint and does not extend the independent 90-day Host grant.

The D1 write is the linearization/commit point for grant state. Enrollment reserves a host id in one transactional compare-and-swap that checks the entire strict static-token id inventory, existing browser row, owner, status, attempt id, and expected prior generation. A new row reserves generation 1; replacement of an expired or revoked row reserves exactly `expected_prior_generation + 1`. Concurrent attempts for one id have one winner; the loser receives a bounded conflict with no owner disclosure. Activation is one transaction conditional on `status=pending`, exact owner, attempt id, reserved generation, unexpired pending deadline, and matching grant digest; it changes status to active without another generation bump. The D1 activation commit is the point at which that generation becomes an authorization grant. No Worker route treats a grant as active before that transaction commits. Revoke is one transaction conditional on exact owner and current active generation; it records the revocation operation id, changes status to revoked, advances generation once, and appends a fencing outbox row. D1 commit makes revocation effective immediately for all subsequent checks. A retry with the same operation id returns the same committed generation and does not bump it again. A stale operation with a different id or generation cannot undo the tombstone.

An interrupted local `Revoking` profile is reconciled against the exact owner, host, grant, operation id, committed generation, and root set. Once revocation is confirmed, remove that local profile and require a fresh `fabric connect` with new owner/root confirmation and new attempt ids. Never resume the attempt that preceded the terminal revoke.

Every Worker route that dispatches or returns Host work, every MCP tool call for browser mode, and every Link connect/poll/respond operation re-reads or validates a generation-fenced D1 authorization snapshot; absent rows, DB errors, owner mismatch, expiry, revoked status, and generation mismatch deny. The Gateway DO stores auth mode, owner key, grant id, and grant generation as transport state and only accepts a server-built internal authorization envelope after the Worker has stripped caller-supplied internal headers and validated D1. The DO rejects a different mode or generation for an existing lease and never promotes legacy transport state into browser mode. A post-commit fencing outbox retry is idempotent by `(host_id, committed_generation)`; while the fence is pending, D1 denies requests and Worker discards responses if the final D1 recheck no longer matches. Work already dispatched before a revoke commit cannot be rolled back, but no new or queued operation or response is admitted after the commit. If D1 or the fence/outbox cannot establish a safe generation, fail closed.

For new Link requests, Cloudflare Managed OAuth's opaque access token remains in `Authorization: Bearer ...` for edge validation. The Worker consumes only the signed `Cf-Access-Jwt-Assertion` identity and checks the custom Host grant header against the owner-host record. This resolves the current bearer-header collision. The old mode continues using `Authorization: Bearer <static host token>`, optional Access Service Token headers, and `HOST_TOKENS_JSON`; it is an independent compatibility mode.

For browser-mode `/mcp` and browser-mode dashboard surfaces, use an explicit route allowlist. The first release allows only identity lookup/enrollment/revoke, owner-filtered live Host discovery, and live session routing for operations that pass the atomic root contract. It denies `context_resolve`, `context_status`, the static `OBSERVATION_OWNER_ID` context path, dashboard data APIs, `fabric_overview`, `fabric_session_list`, `fabric_session_read`, mentions, interaction, observation ingestion, observation replicas, and derived observation projections. Static HTML/JS/CSS resources may be served only if they contain no owner data and cannot call an unguarded data endpoint. Existing cloud events remain unsupported. Any browser-mode route not explicitly allowlisted is denied by default until it proves the same verified owner, active grant generation, and canonical root namespace. No browser identity is mapped onto the existing shared observation owner.

The Worker applies owner and root checks to live Host discovery and every routed request, not only `/v1/hosts/*`. Browser OAuth callers see only Hosts registered to their verified owner; `CLIENT_TOKEN` callers do not gain access to browser-enrolled Hosts. Grant status and approved root names are authoritative in D1; a missing/unavailable row or database error denies the new mode. The Gateway DO lease remains transport state and is not treated as ownership. Host id, transport generation, and enrollment grant generation are distinct values and are all validated at the boundary.

## Local credential storage and revocation

Use a small credential-store interface backed by the macOS Keychain on macOS and Secret Service on supported Linux/WSL2 installations. Store one versioned credential record as one secure-store item scoped to Fabric origin, owner key, and host id. The record contains schema/version, the pinned issuer, public client id, authorization/token endpoint identities, OAuth access and refresh tokens with expiry, Host grant, grant id and generation, the local HMAC fingerprint key, approved root names and local fingerprints, exact Supervisor instance/scope revision, active/pending status, pending enrollment attempt and idempotency ids, cancellation status, refresh attempt id and in-flight/commit-pending/unknown status, and last committed refresh attempt id. Before sending a saved refresh token, compare the configured issuer/client and freshly discovered authorization/token endpoints with these stored pins. A mismatch triggers fresh browser authentication and same-owner verification before replacing the pins; it never sends the old refresh token to the changed endpoint or client. A refresh-token rotation or enrollment-state transition replaces the whole record atomically; the backend must support atomic item replacement and read-back under the process lock or be treated as unavailable. Short-lived access tokens may instead remain in memory, but refresh and Host-grant state must be in this atomic record. Do not split a rotation across independently updated secure items.

Enrollment, refresh, reauth, logout, and revoke acquire one owner-only interprocess state-transition lock scoped to this profile, then re-read the latest secure record before changing it. Release the lock when each finite local/D1 transition completes; never retain it for the Link lifetime. A separate process-owned OS advisory lifetime lock prevents duplicate Link processes and is released automatically on process exit; it is not needed for revoke/logout. This prevents same-machine parallel commands from overwriting refreshed tokens or a pending cancellation without blocking revocation. Server-side D1 compare-and-swap remains the cross-machine authority. If locking is unavailable, a stale record version is observed, atomic replacement fails, or a required read-back does not match the newly committed version, halt the affected operation and Link; never continue with stale in-memory credentials. A record found with `refresh_in_flight`, `refresh_commit_pending`, or `refresh_outcome_unknown` requires interactive reauth. If the OS store is unavailable, locked, or cannot persist the entire record, return a clear error and do not start the browser-enrolled Link. Do not write a file fallback, prompt for an external password manager, or copy a token into an environment variable. Native Windows has no browser enrollment support in this phase.

`temote fabric revoke --host-id <id>` performs an owner-authenticated remote revocation using the stored expected grant generation and stable operation id, then invalidates the Host grant and lease. Repeating the same revoke id after timeout returns the same D1 result; it cannot bump generation twice. `temote fabric logout` serializes against refresh, revokes each local Host grant before deleting its credential record, and removes OAuth credentials only after all requested remote revocations are confirmed. Neither operation waits for or acquires the lifetime Link lease. If the Worker cannot confirm revocation, preserve the local credentials and report that logout did not complete; an explicitly named local-only erase can be a separate later operation because it leaves a live remote grant until expiry. Revoke and logout outputs contain only bounded status, host id, and expiry. D1 commit is effective on the next authorization check; the Link receives a local stop signal when possible and otherwise exits at its next authorization failure.

Use separate lifetimes: OAuth access-token lifetime comes from Cloudflare metadata/configuration (recommended 5–15 minutes); the Cloudflare refresh grant lifetime is set by Access (recommended 1–2 weeks); a pending enrollment expires after 5 minutes; an active Host grant has a bounded 90-day expiry and is not extended by Link heartbeats. An expired Host grant requires a fresh owner-confirmed enrollment. These are initial defaults for review, not claims about a live Access configuration.

## Review acceptance criteria

- One interactive `temote fabric connect` flow can authenticate, confirm owner and roots, activate a Host grant, and enter the unchanged outbound Link loop without manual token transfer.
- OAuth caller identity, host grant possession, owner-host binding, grant expiry/revocation, global host-id collision, and parallel enrollment are independently enforced; `CLIENT_TOKEN` cannot enroll a Host.
- Only approved named roots can be started or used by existing-session tools; discovery is filtered; unknown session scope and missing Supervisor root metadata fail closed.
- OAuth opaque access tokens are never decoded as JWTs by the CLI or Worker. The origin validates only `Cf-Access-Jwt-Assertion`; OAuth bearer and Host grant use separate headers and authorization checks.
- Ctrl-C, lost enrollment responses, concurrent refresh, invalid refresh grants, keychain failure, and Access denial have deterministic retry/stop behavior and never print secret values.
- macOS Keychain is the primary supported secure store. Linux/WSL2 works only with an available supported Secret Service. Unsupported or unavailable storage fails closed without plaintext persistence.
- Existing static host-token/service-token and legacy session-agent modes continue to work without automatic migration or downgrade.

Review the implementation against these cases using isolated fake secure stores, browser opener, HTTP client, D1, Durable Object, and Supervisor inventory/admission implementations. Never use the real Keychain, Secret Service, browser profile, Access app, or credential files in tests.
