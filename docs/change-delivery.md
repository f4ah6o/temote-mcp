# Managed Changes and delivery

A Change is an explicit, durable unit of writable work. Task IDs, execution IDs, Change IDs, and workspace IDs are distinct. Creating a task or subagent does not create a Change or PR. Ordinary tasks in sessions without a managed Change binding keep their existing behavior.

The first ready managed session is the **Change owner** for one repository graph. Its full session instance remains the authority for Change commands. Each Change has its own allocation receipt and execution session. A sibling allocation calls the existing typed managed repository provisioner with a stable operation ID; the provisioner creates its own named-root preparation session and then a separate normal workspace session. The Change owner gains no permission to write into that sibling session, and the executor cannot borrow the owner's session identity. A stopped or replaced owner or executor fails the full-instance check.

`create` takes a stable operation ID, task ID, explicit base, and optional parent IDs. Replaying it checks the entire request. The same task cannot silently acquire a second Change in one owner scope. A supplied `parent_change_id` must agree with `base_change`; a parent task alone never selects a delivery base. `allocate` first records an intent, then uses the managed provisioner. An accepted retry uses the same operation ID and reconciles its receipt. Ready workspace identity, repository, named root, base, and full executor session are checked before binding. Two sibling Changes cannot bind the same mutable workspace. A Change based on another Change can allocate only after the parent's exact revision has completed reconciled delivery; its provisioned source base is the parent's `temote/<change_id>` ref. Git and unsupported source branch capabilities fail explicitly.

The local `change --provisioning-operation-id UUID --request JSON` command and the versioned local task packet `operation: change` expose the same typed Change commands. The local packet carries `owner_provisioning_operation_id` and the ordinary full `SessionInstance` fence, including permission mode, permitted directories, and grants. `list` and `get` return bounded projections rather than execution history. Caller JSON cannot supply an authoritative PR receipt.

For a Ready managed allocation, use `create_ready` with a stable Change `operation_id`, the Ready `allocation_operation_id`, and a separate Codex `task_operation_id`. Temote reads the allocation's full execution session, derives the backend task ID from that session and task operation UUID, creates the explicit Change in the owner graph, and binds the workspace before task startup. The first owner allocation preserves its provisioned Change ID and uses its provisioning UUID as both Change and allocation operation IDs. A sibling allocation uses its own Ready provisioning receipt and an independent Change operation ID. `base`, `parent_task_id`, and `parent_change_id` remain explicit. Exact retries replay the same identities; a changed task operation or base conflicts. The older `create` and `create_provisioned` commands remain available for callers that already know the authoritative task ID.

1. Bring up a managed session and wait for its provisioning receipt to reach `WorkspaceReady` (or use an already Ready sibling allocation).
2. From the Change owner, call `create_ready` with that allocation UUID, a stable Change operation UUID, a fresh task operation UUID, and the explicit base/parent fields. Keep the returned Change ID.
3. Call `start` for that Change with the same task operation UUID, task text, model, and effort. It returns `pending_snapshot` while the delegated jj snapshot is running.
4. Retry the exact `start` request until it returns the mutating task view; then use ordinary task get/control with the returned task ID.

Then call `start` with that Change ID, the same `task_operation_id`, the task text, model, and effort. The first call reserves the Change start and its execution generation, persists a VCS Accepted receipt before helper dispatch, starts a separate Codex jj snapshot task in the allocated session, and returns `pending_snapshot`. Retry `start` with the exact same request. The retry uses TaskGet to reconcile the retained snapshot task; only its completed native structured report with matching operation, task, workspace, execution, and jj before/after state is imported as a completed VCS receipt before the Change advances. A missing or unavailable retained receipt after reservation is `reconciliation_required`; Temote does not launch a second snapshot or infer a pre-start state from later files. The completed snapshot receipt is recorded before the mutating task receives its backend start. Generic MCP/local starts in a bound Change workspace are blocked; the typed snapshot, Change start, delivery, and read-only delivery observer use server-owned admission checks. Other sessions keep generic task behavior. Initial Change start currently supports Codex; other backend first-start capabilities are explicitly unsupported.

After a Change is explicitly bound to a workspace and task, terminal task start/get/control boundaries record its canonical `execution.id`, generation, completed VCS receipt, TaskRecord revision, and current verification. A stable snapshot operation ID derives from Change, execution, and TaskRecord revision. Running and waiting projections leave the VCS and Change revision unchanged. A nonblocking cross-process admission guard serializes each bound task probe/control with its snapshot reservation; a competing caller retries the same operation ID. Pending snapshot receipts block resume and steer. Repeated terminal views reconcile the same helper receipt. Writer generations fence one execution at a time; a terminal execution retains its writer lease until the delegated snapshot receipt and observation are reconciled. Only the exact bound task is observed; delivery observers and unrelated tasks do not gain a Change.

Verification applies to one TaskRecord revision and exact materialized VCS revision. A later task revision or snapshot invalidates it. `delivery::plan` orders explicit Change dependencies and refuses active writers, stale verification, missing workspaces, cycles, and incompatible owners. It fixes head/base refs and revisions in a fingerprint. Planning does not mutate a checkout or create a PR.

`deliver` persists an Accepted receipt before starting a Codex delivery task in that Change's own execution session through exact typed internal admission. The task inspects remote state, publishes only the verified revision, and creates or updates one matching PR. Accepted retries read an exact retained task receipt and never start another task. `reconcile_delivery` uses a separate typed read-only delegated observer; only an exact remote branch/PR observation can complete the receipt. Stacked delivery also requires the observed parent PR number and stack link. No merge is automatic. Workspace release is blocked while delivery or VCS receipts are uncertain.

Live GitHub, gh-stack, and host jj acceptance remain separate gates. A completed delegated execution is not proof of verification or delivery.
